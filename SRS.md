# specdeck — software requirements specification

**Revision:** generated 2026-10-14 00:49 UTC from commit 7bfba8c · **Prepared to:** ISO/IEC/IEEE 29148:2018, content of §9.6 (identification §9.2.1)

## Tailoring

This document is generated by specdeck for tailored conformance (§4.5.2) to the information-item content of ISO/IEC/IEEE 29148:2018 §9.6. The requirements, their attributes (§5.2.8), their verification status and their traceability to tests come from the project's requirements file and its last test run. Sections the project has not written are marked *to be supplied*. Verification by test is automated; inspection, analysis/simulation and demonstration (§6.5.2) are recorded as declared on each requirement. Life-cycle processes (Clause 6) are outside this document.

## 1 Introduction

### 1.1 Overview (§9.6.1)

74 requirements, verified against the test suite of this project.

### 1.2 Purpose (§9.6.2)

specdeck makes a pytest suite its own requirements specification. Requirements are written once, with their rationale; tests are linked to the requirements they verify; and the specification is generated from every run, so it reports which requirements are verified now and cannot drift from the tests.

### 1.3 Scope (§9.6.3)

specdeck is a pytest plugin and command-line tool. It generates the scenario spec from a test run, reads and checks a requirements file, joins the two into verification status, writes documents for people (the specification, a pull-request report) and for coding agents, and serves a local viewer with run history. It does not run tests itself beyond invoking pytest, and it does not carry out the life-cycle processes of ISO/IEC/IEEE 29148 Clause 6.

### 1.4 Product perspective (§9.6.4)

specdeck runs inside pytest as a plugin and reads only what pytest and the project provide. proofdeck, a separate tool, supplies the mutation evidence that `specdeck trust` joins with the requirements to separate proven requirements from passing ones.

### 1.6 User characteristics (§9.6.6)

Python developers and QA engineers who write pytest suites, reviewers who read pull requests, and coding agents that work in the repository. No knowledge of the standard is assumed; its terms are used and cited where they apply.

### 1.7 Limitations (§9.6.7)

Verification by test is automated; inspection, analysis or simulation, and demonstration are recorded as declared on each requirement, not carried out. The quality checks cover the criteria of §5.2.4–5.2.7 a tool can check; appropriate, feasible and correct need review.

### 1.8 Assumptions and dependencies (§9.6.8)

Python 3.10 or later and pytest. The viewer needs a local browser; coverage mapping needs coverage.py.

### 1.9 Apportioning of requirements (§9.6.9)

specdeck owns the requirements, their traceability to tests, the generated documents and the viewer. proofdeck owns mutation evidence: which tests notice a changed line.

#### `deps.document-only`

A dependency shall order reading and reporting, and not test execution.

- **Rationale:** specdeck is added to other people's test suites. Each extra dependency is a version conflict waiting in someone else's environment. Optional features (coverage mapping) load their libraries when asked for.

### 2.7 Standards compliance (§9.6.17)

#### `req.attributes`

Each requirement shall carry the attributes of ISO/IEC/IEEE 29148:2018 §5.2.8 under the standard's names, with its type from §5.2.8.3 and its verification method from §6.5.2.

- **Rationale:** What a requirement records about itself — why it exists, how much it matters, who owns it, how it is verified — is what makes a specification usable. Under the standard's names, a reader who knows 29148 needs no translation, and a specdeck requirement is a requirement in the sense every requirements engineer uses.
- **Type:** standards-compliance
- **Verification method:** test
- **Implements:** ISO/IEC/IEEE 29148:2018 §5.2.8
- **Verification status:** met — verified by `tests/test_requirements.py::test_requirements_carry_the_attributes_of_29148`

#### `req.quality`

`specdeck validate` shall report each requirement and requirement set that departs from the quality criteria of ISO/IEC/IEEE 29148:2018 that a tool can check, citing the clause.

- **Rationale:** The standard defines what makes a requirement good (§5.2.4 construct, §5.2.5 individual characteristics, §5.2.6 set characteristics, §5.2.7 language). Checking them where a machine can, and naming the clause, turns a 100-page standard into feedback on the line someone just wrote. The criteria that need judgement (appropriate, feasible, correct) are left to people.
- **Type:** standards-compliance
- **Verification method:** test
- **Implements:** ISO/IEC/IEEE 29148:2018 §5.2.4–5.2.7
- **Verification status:** met — verified by `tests/test_validation.py::test_requirement_quality_is_checked_against_29148`

#### `req.consistent-examples`

`specdeck validate` shall report a requirement whose examples give two expected values for the same inputs.

- **Rationale:** A set is consistent when no requirement contradicts another (§5.2.6). A requirement that gives two answers for one input contradicts itself, and any test checked against it passes or fails by which example it picked.
- **Type:** standards-compliance
- **Verification method:** test
- **Implements:** ISO/IEC/IEEE 29148:2018 §5.2.6
- **Verification status:** met — verified by `tests/test_validation.py::test_the_set_is_checked_for_consistency_under_29148`

#### `req.consistent-tests`

`specdeck validate` shall report a linked test that asserts a literal value for an example's inputs that differs from the example's expected value, with the test's file and line.

- **Rationale:** A test written with a number instead of `example()` can drift from the requirement it claims to verify. Then the test and the requirement disagree and cannot both be right (§5.2.6). The report names the place, because one of the two has to change.
- **Type:** standards-compliance
- **Verification method:** test
- **Implements:** ISO/IEC/IEEE 29148:2018 §5.2.6
- **Verification status:** met — verified by `tests/test_validation.py::test_the_set_is_checked_for_consistency_under_29148`

#### `req.srs`

`specdeck srs` shall produce the software requirements specification with the content of ISO/IEC/IEEE 29148:2018 §9.6, in the standard's order, verified from the last test run.

- **Rationale:** The standard defines what a software requirements specification contains. Generating the specification from the requirements and the tests that verify them gives a document a reviewer or auditor recognises, that reports which requirements are verified now, and that cannot drift. Sections only people can write are marked to be supplied, so an incomplete set is visible.
- **Type:** standards-compliance
- **Verification method:** test
- **Implements:** ISO/IEC/IEEE 29148:2018 §9.6
- **Verification status:** met — verified by `tests/test_srs.py::test_the_srs_has_the_content_of_29148_section_9_6`

### 2.8 Software system attributes (§9.6.18)

#### `spec.safe-yaml`

Step text containing a colon shall produce a spec that parses.

- **Rationale:** Unquoted `key: value` inside a scalar silently broke the hand-written specs specdeck replaces; two files were unloadable for months before anyone noticed.
- **Type:** software-attribute
- **Verification method:** test
- **Verification status:** met — verified by `tests/test_generation.py::test_step_text_with_colons_stays_parseable`, `tests/test_validation.py::test_unparseable_yaml_reports_a_line`

#### `run.partial-safe`

A partial run shall keep the scenarios outside the run in the spec.

- **Rationale:** `-k` collects a subset; rewriting the spec from it would delete every scenario that did not run. The default refuses, and --specdeck-merge updates in place.
- **Type:** software-attribute
- **Verification method:** test
- **Verification status:** met — verified by `tests/test_maintenance.py::test_partial_run_can_merge_instead_of_skipping`, `tests/test_maintenance.py::test_merge_without_an_existing_spec_explains_itself`, `tests/test_maintenance.py::test_partial_run_still_refuses_by_default`

#### `req.malformed-entry`

A malformed requirements entry shall be reported and skipped, with the rest of the file used.

- **Rationale:** One bad entry should not cost a team its whole traceability report. The problem is named, and the other requirements are still verified.
- **Type:** software-attribute
- **Verification method:** test
- **Verification status:** met — verified by `tests/test_requirements.py::test_problems_in_the_file_are_reported_not_fatal`

#### `context.coverage-unavailable`

When coverage cannot be recorded, the run shall continue and report that the map is missing.

- **Rationale:** Asking for a map and silently getting none is the worst outcome: the agent document would be missing its most useful half with no sign of the gap. The tests still run.
- **Type:** software-attribute
- **Verification method:** test
- **Verification status:** met — verified by `tests/test_context.py::test_a_recorder_that_cannot_start_stays_inert`, `tests/test_context.py::test_a_run_that_cannot_record_coverage_says_so_instead_of_going_quiet`

#### `history.abandoned`

A run whose pytest process stopped before finishing shall be marked abandoned.

- **Rationale:** A run left as "running" forever makes the board lie and blocks the next comparison. A dead process is detected and named.
- **Type:** software-attribute
- **Verification method:** test
- **Verification status:** met — verified by `tests/test_history.py::test_a_run_whose_process_died_is_marked_abandoned`

#### `viewer.local-only`

The viewer shall refuse a request whose Host is not loopback, and a write without the page's token.

- **Rationale:** The viewer can edit and run code. Refusing foreign hosts stops DNS rebinding; requiring the page's token stops another site from posting to it.
- **Type:** software-attribute
- **Verification method:** test
- **Verification status:** met — verified by `tests/test_server.py::test_writes_need_the_token_and_a_loopback_host`

#### `edit.refuse-stale`

The editor shall write nothing for an edit made to an outdated version of the test or to computed text.

- **Rationale:** Writing over a test that changed since it was loaded would lose someone's work; editing text the code computes would edit something that is not in the file. Refusing writes nothing at all.
- **Type:** software-attribute
- **Verification method:** test
- **Verification status:** met — verified by `tests/test_editing.py::test_stale_forms_and_computed_text_are_refused`

### 2.9 Process requirements (§5.2.8.3)

#### `process.self-check`

A change to specdeck shall leave `specdeck validate` reporting no findings on specdeck's own spec and requirements.

- **Rationale:** specdeck checks other projects against ISO/IEC/IEEE 29148:2018; its own requirements and tests are the first place that check has to pass. A finding left behind is a requirement that is unverified, ambiguous or untraced.
- **Type:** process
- **Verification method:** demonstration
- **Verification status:** by demonstration (declared)

#### `process.generated-docs`

SRS.md and the rules in AGENTS.md shall be regenerated from a full run before a change is committed.

- **Rationale:** Both are generated, so they are only as current as the run they came from. A committed SRS that disagrees with the tests is the drift specdeck exists to prevent.
- **Type:** process
- **Verification method:** inspection
- **Verification status:** by inspection (declared)

#### `process.standard-text`

The repository shall cite ISO/IEC/IEEE 29148:2018 by clause number, in specdeck's own words.

- **Rationale:** The standard is copyrighted. Clause references let a reader with a copy check each claim, and the descriptions stay ours.
- **Type:** process
- **Verification method:** inspection
- **Verification status:** by inspection (declared)
