# Agent A/B: does the generated spec help an agent, or do the test files do just as well?

The one thing the research behind specdeck could not answer from the literature:
whether a coding agent reasons better about a suite from a *generated scenario
spec* than from the raw tests the spec was generated from. This folder measures
it on tapedeck (38 tests, 1.7k source lines) with `gpt-5.6-terra`.

## Design

Three arms get the **same model, the same questions and the same answer
format**; only the material differs:

| arm | material | tokens |
|---|---|---|
| `spec` | `.specdeck/spec.yaml`, generated by specdeck from the suite | 8.4k |
| `tests` | `tests/conftest.py` + `tests/test_*.py`, verbatim | 12.8k |
| `both` | spec + tests | 21.2k |

The spec is **derived from** the tests, so every arm holds the same facts; the
experiment is about the *representation*, not about information one arm lacks.
What differs: the spec has status stamps, scenario ids and an explicit
`depends_on` graph; the tests have the code.

Two tasks, both with mechanical ground truth (`groundtruth.py`), neither of
which consults the spec when building questions:

- **Impact** — "line N of `path` changes from X to Y; which tests fail?"
  32 questions: 24 changes a test catches, 8 nobody catches. The mutants are
  proofdeck's operators (boundary, negation, arithmetic, constant, deleted
  statement). Truth: apply the change, run the whole suite with specdeck's
  prerequisite-skipping off, record the failures. Scored as precision/recall/F1
  over the set of test functions.
- **Triage** — "after one change these tests did not pass; which failed on
  their own, which were only blocked by a failed prerequisite, and which single
  failure do you fix first?" 10 runs, each with a real cascade. Truth: the same
  mutant run with specdeck on (`FAILED` vs `SKIPPED … blocked`); fix-first is
  the direct failure holding up the most others, computed from the DAG.

Questions are batched (8 impact / 5 triage per call) so the ~10–20k-token
context is paid once per batch, and the three arms interleave per batch so an
exhausted budget leaves every arm with the same questions answered.

## Token accounting

Every call is appended to `calls.jsonl` with the API's own usage numbers
(prompt, cached, completion, reasoning). `run.py` estimates each call with
tiktoken before making it and stops when the next call would pass `--budget`
(default 500,000). `grade.py` writes `RESULTS.md` with the scores and the
per-arm token table.

```bash
python groundtruth.py          # ~90 s: builds data/impact.json and data/triage.json
python run.py --budget 500000  # resumable; skips (task, arm, batch) triples already logged
python grade.py                # RESULTS.md + results.json
```

Model notes: `gpt-5.6-terra` rejects `temperature`; it was left at its default
reasoning effort (about 2–3k reasoning tokens per call) and asked for
`json_object` output.

## Result (2026-10-01, 18 calls, 343,197 tokens of the 500,000 budget)

Full tables in `RESULTS.md` (regenerated by `grade.py`); the log of every call,
with the API's usage numbers, is `calls.jsonl`.

| task | spec | tests | both |
|---|---|---|---|
| Impact, mean F1 (n=32) | 0.80 | **0.93** | **0.93** |
| Impact, exact set | 59% | **88%** | **88%** |
| Triage, mean F1 (n=10) | 0.77 | 0.78 | 0.77 |
| Triage, fix-first right | 100% | 100% | 100% |
| Tokens for the whole run | **80k** | 106k | 158k |

Reading it honestly:

- **For "which test fails if this line changes", the test code wins and the
  spec adds nothing to it.** The spec alone is 0.13 F1 behind; given tests and
  spec together the model answers exactly as it did with the tests alone. The
  spec narrates what a test checks; the code says *how*, and that is what
  predicting a failure needs. Still, from Given/When/Then prose alone the agent
  reached 0.86 F1 on changes a test catches — the spec carries most of the
  signal, not all of it.
- **For triage over the dependency graph the three arms are indistinguishable**,
  down to making the same mistakes on the same runs: every arm systematically
  calls too few tests *direct* failures and too many *blocked*, i.e. it reads
  `depends_on` as a chain when the real cascade has several independent roots.
  Both the YAML `depends_on` and the decorator `depends_on` were read equally
  well (or equally badly). Fix-first was right every time in every arm.
- **The spec is the cheapest material**: the whole run cost 80k tokens against
  106k for the tests, for the same triage answers. On a suite this size
  (12.8k tokens of tests) that is the only advantage measured.

What this does *not* say: the suite is small enough that the raw tests fit in
context trivially, so the compression the spec offers never had to matter; one
model, one sample per question, batched prompts. The result that would change
the picture is a suite whose tests do not fit (10× this one), or an agentic
task (edit code until green) where the spec's status stamps and fix-first
ordering could steer the loop. Neither was run.

## Round 2 — the gap was a design flaw in the spec, not a limit of specs

Round 1 was not a fair fight and it was read too quickly. The arms were not matched
on tokens (8.4k against 12.8k), so the headline was a handicapped contestant losing.
The useful question is what the test files carry that the spec does not, and whether
the spec can carry it. The answers came out of the logged responses.

**Diagnosis 1 — the spec names no source code.** It says *"Given a proxied toy web
client whose responses are dict-like"*; the test file says
`from tapedeck import GatewayApp`. Asked "line 31 of `gateway/app/app.py` changed,
which tests fail?", the spec arm has no bridge from that file to any scenario. One
`app.py` question accounted for 17 of its 25 missed failures.

**The fix, measured.** `enrich.py` adds a coverage map — which scenarios execute
each source function, recorded by tracing the suite once, import-time lines excluded
(they belong to every test and discriminate nothing). Scenarios are numbered so each
reference costs one token: 3,091 tokens for the whole map.

| impact task, 32 questions | spec | **spec + map** | tests | both |
|---|---|---|---|---|
| mean F1 | 0.80 | **0.88** | 0.93 | 0.93 |
| exactly right | 59% | **78%** | 88% | 88% |
| real failures missed (of ~110) | 25 | **4** | 2 | 2 |
| failures invented | 18 | 35 | 31 | 31 |
| tokens per question | 1,750 | 2,181 | 2,274 | 3,355 |

The map closes about two thirds of the gap and all but eliminates the *missing*
failures — 25 down to 4, against 2 for the test files — at a slightly lower cost per
question. It does not win outright. What is left is over-prediction, and the spec arm
is now at parity with the tests arm there (35 against 31): both name tests that
*run* the changed line but would not actually notice. That is not a prose problem,
it is the checked-versus-ran-only distinction — **the question proofdeck answers
mechanically**. Neither reading material can settle it, which is the argument for
the trio rather than for a better spec.

**Diagnosis 2 — the spec prints `depends_on` without saying what it means,
and triage was never a judgement call.** Solved straight from the DAG:

| rule applied to the dependency graph | F1 | exactly right |
|---|---|---|
| "anything upstream failed, so you were blocked" | 0.74 | 40% |
| "blocked only by a prerequisite that **already ran**" | **1.00** | **100%** |

Every model arm scored 0.77 at 40% exact — what the *wrong* rule scores, give or
take. The model was not reasoning badly; it was applying the obvious rule correctly.
The obvious rule is wrong because specdeck never reorders tests, so a prerequisite
listed later cannot block anything, and the spec never says so. A reader has no way
to know. The answer is exact and specdeck already computes it in the viewer — it is
simply not in the spec.

## Round 3 — the 100-token fix

Diagnosis 2 said triage was exactly solvable and every arm scored the wrong rule's
number. Round 3 tested the cheapest possible repair: state the rule, in one short
paragraph, and give the *same* paragraph to the test-file arm so a gain can be
attributed to the fact rather than to the format.

| triage, 10 runs | spec | spec + rule | tests | tests + rule |
|---|---|---|---|---|
| mean F1 | 0.77 | **1.00** | 0.78 | **1.00** |
| exactly right | 40% | **100%** | 40% | **100%** |
| cost of the paragraph | — | 100 tokens | — | 100 tokens |

Perfect, from both sides. The win is the **fact**, not the representation — which is
the honest reading, and it is also the argument for putting it in the spec: nobody
writes that paragraph into their test files, and specdeck can emit it every run
because it is a property of specdeck's own semantics.

## Rounds 4 and 5 — shipped, then re-measured

Both fixes went into specdeck proper: `pytest --specdeck-coverage` records the map
(coverage.py, one extra second on 38 tests, import-time lines excluded), and
`specdeck context` writes the document. The `shipped` arm below is that command's
real output, not a prototype.

| | spec | shipped | tests |
|---|---|---|---|
| impact F1 | 0.80 | **0.88** | 0.93 |
| triage F1 | 0.77 | **1.00** | 0.78 |
| triage exactly right | 40% | **100%** | 40% |
| context tokens | 8,431 | 11,962 | 12,773 |

The shipped document reproduces both prototype gains. Against the raw test files it
now **wins decisively on triage, trails modestly on impact, and costs less**. The
remaining impact gap is entirely the "nobody notices this change" half of the
questions (0.62 against 0.75) — the one question no reading material answers, and
the one `proofdeck check` answers mechanically.

## Round 6 — a second subject, three times the size

The standing caveat on everything above was that tapedeck's whole suite fits in context
with room to spare, so the spec's compactness never had to matter. Round 6 repeats the
impact task on specdeck's own suite: 88 tests, 226 source functions, and a spec that
saves 5k tokens rather than 4k. 16 questions, same ground-truth machinery.

| impact, specdeck as subject | spec | shipped | tests |
|---|---|---|---|
| mean F1 | 0.70 | **0.71** | 0.71 |
| exactly right | 38% | **44%** | 44% |
| real failures missed (of 48) | 9 | **8** | 12 |
| failures invented | 8 | 7 | 3 |
| context tokens | 17,973 | 25,745 | 30,749 |

Two things changed, and they point opposite ways.

**The spec's deficit did not generalize — it vanished.** On tapedeck the raw test files
beat the shipped document 0.93 to 0.88; here they tie, at 16% fewer tokens, and the
document actually *misses fewer real failures* (8 against 12) while being less
cautious about inventing them. Round 1's headline, "the test files are simply better
material", is a tapedeck result, not a general one.

**The coverage map's gain did not generalize either.** It was worth +0.08 F1 on
tapedeck and +0.01 here. Not because the map is worse — it is *more* discriminating on
specdeck (129 of 226 functions are touched by fewer than a tenth of the scenarios,
against 38 of 116 on tapedeck). The reason is that **everybody got worse**: the test
files fell from 0.93 to 0.71 too. On a suite whose tests run pytest inside pytest,
knowing which function a line belongs to stops being the bottleneck.

What becomes the bottleneck is visible in one number: on the four changes that **no
test notices**, all three arms wrongly cried failure on three of them. That is the
"would a test actually notice" question, it is where the remaining error lives on both
subjects, and it is the one `proofdeck check` answers by running the mutant instead of
reasoning about it.

## Rounds 7 and 8 — reading the large-suite failures

Round 6 said "everyone gets worse on a bigger suite". Looking at the logged answers
instead of the scores said something much narrower.

**First, 28% of round 6's ground truth was wrong.** specdeck's suite runs pytest inside
pytest, and the scraper collected `FAILED` lines from those nested runs — node ids like
`test_pricing.py::test_parse` that exist only in a temp directory and that no reader of
the repo could ever name. `groundtruth.py` now filters failures against what the suite
actually collects. Re-scoring the same answers moved every arm up about 3 points.

**Second, the real task was never the problem.** On the 12 changes that genuinely break
something, every arm is strong and nearly identical — precision 83–92%, recall 88–98%,
with the shipped document highest on recall. The collapse was entirely on changes that
break *nothing*, and mostly on a single question: a config line inside `pytest_configure`,
which 47 of 88 scenarios run.

| named on that question (true answer: no test fails) | |
|---|---|
| bare spec | 9 |
| spec + coverage map as a list | **87** |
| + "the map is a bound" | 50 |
| + hub functions collapsed to a count | **9** |
| raw test files | 10 |

The map had made the agent *worse*, by handing it a long list that reads as evidence and
is nothing of the kind: it is the same list for every change in that function. Two fixes,
both now in `specdeck context`:

1. **State that the map is a bound** — the listed scenarios are the only ones that can
   fail; a function absent from the map is run by nobody; module-level lines are outside
   the bound because import-time lines are excluded. Impossible answers (naming a test
   that does not execute the changed function) fell from **43 to 5**.
2. **Collapse hub functions to `most (N of M)`** when a function is run by at least half
   the suite and at least 8 scenarios. Both conditions matter: on a small suite "3 of 4"
   is still the answer.

Across all 16 questions, counting what a developer would actually have to chase:

| | names given | right | **wrong names to chase** |
|---|---|---|---|
| spec + map as a list | 137 | 40 | **97** |
| + bound rule | 99 | 39 | 60 |
| + hub collapsed | 57 | 39 | **18** |
| raw test files | 52 | 36 | 16 |

Same number of correct answers, a fifth of the noise, and the document is 10% shorter.
Mean F1 barely moves (0.74 → 0.73) because the noise concentrates on questions whose
score is zero either way — a reminder that the headline metric was the wrong instrument
for this effect, and that the per-answer counts had to be looked at directly.

## Rounds 9 and 10 — where the instructions go

The round-8 fixes cost something elsewhere: on tapedeck, sorting real failures from
blocked ones fell from 100% exact to 70%, and the drop tracked how much text had been
added (the lighter `bound` variant landed at 80%). The new coverage rules were out-
competing the `depends_on` rule, and they sat *later* in the document.

Round 9 shortened the coverage notes **and** moved the blocking rule to the end — two
changes at once, so round 10 separated them.

| tapedeck | which tests break (score) | real-vs-blocked exact | fix-first |
|---|---|---|---|
| long notes, rule first (`hub`) | 0.89 | 70% | 70% |
| short notes, rule last (`order`) | 0.85 | **100%** | **100%** |
| long notes, rule last (`longlast`) | **0.88** | **100%** | **100%** |

The **move** was worth the whole triage recovery; the **shortening** only cost accuracy
on the other task. So: keep the long notes, put the blocking rule last, closest to
whatever is asked next. That is what `specdeck context` emits, and a test pins the
ordering with the measurement in its comment.

On the larger subject the same document is the best of everything measured, raw test
files included — the first arm to beat them on this task:

| specdeck (88 tests) | score | real failures found | wrong names to chase |
|---|---|---|---|
| spec only | 0.73 | 39 / 41 | 20 |
| + map as a list | 0.74 | 40 / 41 | **97** |
| + bound rule | 0.72 | 39 / 41 | 60 |
| + hubs collapsed | 0.73 | 39 / 41 | 18 |
| **+ rule last (shipped)** | **0.79** | **40 / 41** | **11** |
| raw test files | 0.75 | 36 / 41 | 16 |

## Round 11 — four models, two profiles

Everything above was one model. The question that decides whether any of it is real: is
it a property of the documents, or of `gpt-5.6-terra`? `brief` (7.2k tokens) against
`wiring` (12.8k, the raw test files) on both tasks, on three more models.

**Root cause vs blocked — the headline claim:**

| model | brief | wiring (test files) |
|---|---|---|
| gpt-5.6-terra | **100% exact** | 40% exact |
| gpt-5-mini | **100% exact** | 40% exact |
| gpt-5.4-mini | 0% exact (fix-first 70%) | 0% exact (fix-first 30%) |
| gpt-4o-mini | 0% exact (fix-first 10%) | 0% exact (fix-first 0%) |

It replicates **exactly** on the second reasoning model — same 100% against 40%. The two
models that produced no reasoning tokens cannot do the task with either material, so they
do not discriminate; even there the document is ahead on the partial credit.

**Which tests break — the test files win on every model:**

| model | brief | wiring |
|---|---|---|
| gpt-5.6-terra | — | 0.93 |
| gpt-5-mini | 0.59 | **0.71** |
| gpt-5.4-mini | 0.42 | **0.45** |
| gpt-4o-mini | 0.21 | **0.27** |

Four models, same direction every time. That claim is as solid as anything here.

**Tokens for the same 6 calls per arm:**

| model | brief | wiring | saved | cached input |
|---|---|---|---|---|
| gpt-5-mini | 95,854 | 130,489 | −27% | 34,560 / 95,242 |
| gpt-5.4-mini | 58,655 | 93,060 | −37% | 34,560 / 95,242 |
| gpt-4o-mini | 57,166 | 90,601 | −37% | 35,200 / 95,250 |

All three minis cache the repeated document prefix; terra cached nothing. Prompt caching
makes the smaller document cheaper again on every call after the first.

**Caveat on gpt-5.4-mini:** it returned **zero reasoning tokens** and answered in about
four seconds, so it was almost certainly not reasoning at default settings. Its scores
should be read as "this model, asked this way", not as the model's ceiling.

## What this says about designing the spec

1. **Name the code.** A spec that describes behaviour without naming the functions
   behind it cannot be reasoned about alongside a diff. The coverage map is cheap,
   mechanical, and worth two thirds of the gap.
2. **Exclude import-time lines from any coverage specdeck emits.** Unfiltered, all
   38 tests "touch" all 16 files and the map carries no signal at all — the same trap
   the proofdeck trust join hit.
3. **Carry conclusions, not just structure.** Where the answer is a rule, state the
   answer. Handing an agent `depends_on` and hoping cost 60 points of accuracy on a
   question with an exact answer specdeck already knows.
4. **Stop at what the spec cannot know.** Whether a test would *notice* a change is
   not in the spec or the test file; it is in proofdeck. That boundary is where the
   trio earns its keep.
5. **A generated artifact can carry the generator's semantics.** The single largest
   win was writing down a rule about how specdeck runs tests. Hand-written docs drift
   from that; generated output cannot.

The practical conclusion for specdeck: the round-1 verdict ("the spec adds
nothing") was too strong — most of that gap was a fixable omission, and a 3k-token
map recovers two thirds of it for less than the test files cost. But the honest
ceiling still stands: an enriched spec reaches near-parity, not superiority, and the
residual error is one no reading material fixes. specdeck's value to agents is
therefore less "better answers from prose" than **pre-computing the facts agents get
wrong** — coverage, blocked-versus-failed, fix-first — and handing the rest to
proofdeck. Round 2 budget: 69,802 tokens; 413,000 of 500,000 used overall.
