# specdeck — the test suite, for an agent

Generated by specdeck from the tests themselves, so it cannot drift from them.
Each scenario is one test: `logic` is the pytest node id that runs it, the steps are
what it does and checks as recorded while it ran, and `status:` is from the last run.

## Which scenarios execute which code

Each function lists the `n:` of the scenarios that run it. Read it as a bound:

- Those scenarios are the **only** ones that can fail when you change that function.
  Naming any other is wrong. A function not listed is run by nobody — changing its body
  cannot fail any test.
- `most (N of M)` replaces the list where nearly the whole suite runs a function. It is
  the same list for every change there, so it is not evidence; the answer is usually far
  *smaller* than N, never larger.
- Lines that run at **import** are left out (every test runs them). Those are the module's
  top level — constants, class bodies, decorators — and a change there is outside the
  bound.
- Running a function is not checking it, so the true answer is usually smaller than the
  list. Which scenarios would *notice* is not here and is not in the tests either: it is
  what `proofdeck check` measures by changing the line and running them.

## How to read `depends_on`

`depends_on` is documentation order, not execution order: specdeck never reorders
tests, and the scenarios below are listed in the order they run. A scenario is
skipped as *blocked* only when a prerequisite that ran **earlier** did not pass, and
blocking cascades from there. A scenario whose only failed prerequisite runs **later**
is not skipped at all — it runs normally, and can fail on its own.
