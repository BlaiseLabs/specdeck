# specdeck and ISO/IEC/IEEE 29148:2018

specdeck is an executable requirements specification for pytest projects, built on
**ISO/IEC/IEEE 29148:2018**, *Systems and software engineering — Life cycle processes —
Requirements engineering*. That standard replaced IEEE 830-1998 (the classic "SRS" standard)
in 2011 and was revised in 2018.

The standard says what a requirement is, what makes one well-formed, what a specification
contains, and how requirements are verified. It assumes people keep the specification and the
evidence in step by hand. specdeck keeps them in one place: requirements are written with their
rationale, tests are linked to the requirements they verify, and the specification is generated
from each test run, so it reports which requirements are verified *now* and cannot drift from the
tests.

This document maps each concept in the standard to what specdeck does. Clause numbers refer to
the 2018 edition and were checked against the published text; descriptions are our own
summaries, not text from the standard.

**What specdeck claims.** specdeck is *aligned with* 29148:2018. It does not claim full
conformance (4.2), which also covers life-cycle processes a tool cannot carry out. The generated
software requirements specification aims at *tailored conformance* for that one information item
(4.4, 4.5.2): the content of 9.6, with the tailoring declared in the document itself.

## The requirement itself (5.2.4)

A well-formed requirement names its subject and what it shall do (or a constraint on it), is
qualified by measurable conditions, is bounded by constraints, and can be verified. The standard
also sets keyword conventions: *shall* for binding requirements, *will* for statements of fact or
purpose, *should* for goals, *may* for allowances; positive statements rather than "shall not";
active voice. specdeck's requirement `statement` is checked against these conventions by
`specdeck validate` (codes `NOT_SHALL`, `NEGATIVE`, `PASSIVE`, `ABLE_TO`).

## Requirements and their attributes (5.2.8)

The standard recommends that each requirement carry attributes that help identify, understand
and manage it. Its examples (5.2.8.2): identification, owner, stakeholder priority, risk,
rationale, difficulty and type, with type examples in 5.2.8.3 (functional/performance, interface,
process, human factors and others).

| Attribute | In requirements.yaml |
|---|---|
| Unique identification | `id` (`spec.generated`) |
| Requirement statement | `statement` (`says` is still read) |
| Rationale | `rationale` (`why` is still read) |
| Type (5.2.8.3) | `type`: `interface`, `functional`, `usability`, `performance`, `logical-database`, `design-constraint`, `standards-compliance`, `software-attribute` (the sections of 9.6.11–9.6.18), `process`, `human-factors` |
| Stakeholder priority | `priority` |
| Owner | `owner` |
| Risk, difficulty | `risk`, `difficulty` |
| Verification method (6.5.2, 9.6.19) | `verification`: `test` (default), `inspection`, `analysis`, `simulation`, `demonstration` |
| Verification status | `status` in the requirements report: met, failing, blocked, not run, untested |
| Traceability (6.6) | `covers=` links from tests to requirements; the report and the SRS show both directions |
| Standard reference | `standard` (e.g. `ISO/IEC/IEEE 29148:2018 §5.2.8`), used on specdeck's own requirements |

Unknown keys, unknown types and unknown verification methods are reported, citing the
clause.

## Kinds of requirement

The standard's specification content separates what the software does from how well it does it
and from what limits how it may be built.

| Kind | Example | In specdeck |
|---|---|---|
| Functional | "A partial run shall keep the scenarios outside the run in the spec." | `type: functional`, verified by tests |
| Non-functional (performance, usability, software system attributes such as reliability and security) | "The viewer shall refuse a request whose Host is not loopback." | `type: performance`, `usability` or `software-attribute`, verified by tests or analysis |
| Design constraint | "A dependency shall order reading and reporting, and not test execution." | `type: design-constraint`, with its rationale (the decision record) and a test that fails when it is broken (a fitness function) |

Design constraints (9.6.16), standards-compliance requirements (9.6.17) and process
requirements (5.2.8.3, a team's Definition of Done) are the project's rules. `specdeck agents`
writes them into the agent instructions file (AGENTS.md) with their rationale, the tests that
verify them and their status from the last run, so the file is short, current and backed by
checks.

## Characteristics of an individual requirement (5.2.5)

Each requirement should be necessary, appropriate, unambiguous, complete, singular, feasible,
verifiable, correct and conforming. specdeck checks what a tool can check and lists the rest for
review.

| Characteristic | Check |
|---|---|
| Verifiable | **automated**: at least one linked test, or a declared non-test verification method |
| Necessary | **automated, partial**: has a rationale; untraced requirements are flagged |
| Singular | **lint**: flags a statement with more than one "shall" or a semicolon |
| Unambiguous | **lint**: flags the kinds of unbounded terms 5.2.7 says to avoid (superlatives, subjective language, vague pronouns, ambiguous adverbs and "and/or", open-ended terms, comparatives, loopholes such as "if possible", totality such as "always") |
| Complete | **lint, partial**: flags TBD/TBS/TBR placeholders |
| Conforming | **automated**: required attributes present and well-formed (`specdeck validate`) |
| Appropriate, feasible, correct | **review**: judgement; listed in the generated specification's review checklist |

## Characteristics of a set of requirements (5.2.6)

A set should be complete, consistent, feasible, comprehensible and able to be validated.

| Characteristic | Check |
|---|---|
| Complete | **automated**: no TBx; every requirement verified; every test traced to a requirement (`UNTRACED_TEST`) |
| Consistent | **automated**: unique ids; no links to requirements that do not exist (`UNKNOWN_REQUIREMENT`); no requirement with two expected values for the same inputs (`CONFLICTING_EXAMPLES`); no linked test asserting a literal that contradicts an example (`CONTRADICTS_EXAMPLE`). On a branch, proofdeck checks the same against the requirements as approved on the base branch |
| Comprehensible | the generated specification, readable by people and coding agents |
| Able to be validated | examples (given → expect) a stakeholder can check against their intent |
| Feasible | **review** |

## Verification (6.5.2)

The standard names four verification methods: inspection, analysis or simulation, demonstration
and test.
specdeck automates test: each requirement's status comes from the last run of its linked tests.
The other three are declared on the requirement with their evidence (a document, a recording, a
review) so the specification can say how every requirement is verified, not only the tested ones.

With proofdeck, a requirement that passes can also be shown to be *proven*: its tests notice when
the code that implements it is broken (`specdeck trust`).

## The generated specification

`specdeck srs` writes the specification with the content of 9.6 (example outline in
8.5.2): overview, purpose, scope, product perspective, product functions, user characteristics,
limitations, assumptions and dependencies, apportioning of requirements, then the specified
requirements (external interfaces, functions, usability, performance, logical database, design
constraints, standards compliance, software system attributes), verification (9.6.19, as a
traceability matrix: requirement → tests → status), and supporting information. Sections that a
project's requirements file does not fill are listed as not applicable or to be supplied, which is
what 5.2.6 asks of a set that is not yet complete (no hidden TBDs). Every requirement appears with its attributes, its verification status from the last
run, and the tests that verify it.

## specdeck's own suite

specdeck is specified the same way. Its [requirements.yaml](../requirements.yaml) holds 67
requirements, each a "shall" statement with a type, a rationale and a verification method;
those that implement the standard are typed `standards-compliance` (9.6.17) and name the
clause in `standard:`. Its own rules — design constraints and a Definition of Done — are in
[AGENTS.md](../AGENTS.md), generated by `specdeck agents`. Every one of its 99
tests covers at least one requirement, so every test traces through a requirement and,
where one applies, to the clause it implements. `specdeck validate` reports no findings
on specdeck itself, and its own specification is [SRS.md](../SRS.md), generated with
`specdeck srs`.
