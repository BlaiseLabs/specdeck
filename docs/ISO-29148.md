# specdeck and ISO/IEC/IEEE 29148:2018

specdeck is an executable requirements specification for pytest projects, built on
**ISO/IEC/IEEE 29148:2018**, *Systems and software engineering — Life cycle processes —
Requirements engineering*. That standard replaced IEEE 830-1998 (the classic "SRS" standard)
in 2011 and was revised in 2018.

The standard says what a requirement is, what makes one well-formed, what a specification
contains, and how requirements are verified. It assumes people keep the specification and the
evidence in step by hand. specdeck keeps them in one place: requirements are written with their
rationale, tests are linked to the requirements they verify, and the specification is generated
from each test run, so it reports which requirements are verified *now* and cannot drift from the
tests.

This document maps each concept in the standard to what specdeck does. Clause numbers refer to
the 2018 edition; descriptions are our own summaries, not text from the standard.

## Requirements and their attributes (5.2.8)

The standard recommends that each requirement carry attributes that help identify, understand
and manage it.

| Attribute | specdeck today | Plan |
|---|---|---|
| Unique identification | `id` (`spec.generated`) | keep |
| Requirement statement | `says` | accept `statement` as the standard name; `says` stays as an alias |
| Rationale | `why` | accept `rationale`; `why` stays as an alias |
| Type (functional, non-functional, constraint) | none | add `type` |
| Priority | none | add `priority` |
| Source (the stakeholder or document it came from) | none | add `source` |
| Verification method | implied: test | add `verification`: test, demonstration, inspection or analysis |
| Verification status | `status` in the requirements report (met, failing, blocked, untested) | keep; name it verification status |
| Traceability | `covers=` links from tests to requirements | keep; report both directions (requirement → tests, test → requirements) |
| Standard reference | none | add `standard` (e.g. `29148:2018 5.2.8`) for specdeck's own requirements |

## Kinds of requirement

The standard's specification content separates what the software does from how well it does it
and from what limits how it may be built.

| Kind | Example | In specdeck |
|---|---|---|
| Functional | "A partial run never shrinks the spec." | requirement with `type: functional`, verified by tests |
| Non-functional (performance, security, usability, reliability…) | "The suite makes no network calls." | `type: non-functional`, verified by tests or analysis |
| Design constraint | "Use bun, not npm." "Services talk only through the queue." | `type: constraint`, with its rationale (the decision record) and a check that fails when it is broken (a fitness function) |

Constraints and the project's Definition of Done generate the agent instructions file, so
AGENTS.md is short, current and backed by checks.

## Characteristics of an individual requirement (5.2.5)

Each requirement should be necessary, appropriate, unambiguous, complete, singular, feasible,
verifiable, correct and conforming. specdeck checks what a tool can check and lists the rest for
review.

| Characteristic | Check |
|---|---|
| Verifiable | **automated**: at least one linked test, or a declared non-test verification method |
| Necessary | **automated, partial**: has a rationale; untraced requirements are flagged |
| Singular | **lint**: flags statements that join several requirements ("and", "also", lists) |
| Unambiguous | **lint**: flags vague terms that cannot be verified ("fast", "user-friendly", "robust", "as appropriate") |
| Complete | **lint, partial**: flags missing conditions or thresholds where examples are expected |
| Conforming | **automated**: required attributes present and well-formed (`specdeck validate`) |
| Appropriate, feasible, correct | **review**: judgement; listed in the generated specification's review checklist |

## Characteristics of a set of requirements (5.2.6)

A set should be complete, consistent, feasible, comprehensible and able to be validated.

| Characteristic | Check |
|---|---|
| Complete | **automated**: every requirement verified; every test traced to a requirement (orphan tests reported) |
| Consistent | **automated**: unique ids, no test contradicting an approved example (with proofdeck: `contradicts-requirement`) |
| Comprehensible | the generated specification, readable by people and coding agents |
| Able to be validated | examples (given → expect) a stakeholder can check against their intent |
| Feasible | **review** |

## Verification

The standard names four verification methods: inspection, analysis, demonstration and test.
specdeck automates test: each requirement's status comes from the last run of its linked tests.
The other three are declared on the requirement with their evidence (a document, a recording, a
review) so the specification can say how every requirement is verified, not only the tested ones.

With proofdeck, a requirement that passes can also be shown to be *proven*: its tests notice when
the code that implements it is broken (`specdeck trust`).

## The generated specification

`specdeck srs` (planned) writes the specification in the standard's content outline:
introduction (purpose, scope, product overview), specified requirements grouped by kind
(functions, performance, usability, interfaces, design constraints, standards compliance, system
attributes), verification (a traceability matrix: requirement → tests → status), and supporting
information. Every requirement appears with its attributes, its verification status from the last
run, and the tests that verify it.

## specdeck's own suite

specdeck is specified the same way. Each of its requirements references the clause of the
standard it implements (`standard:`), and each of its tests covers at least one requirement, so
every test traces through a requirement to the standard. Today 17 requirements and 44 links cover
about half the suite; the plan links the rest.
